## Context

八字已建立完整管線：`BirthMoment`（當地標準時間、已扣夏令）→ 純函式計算 → `BaziService` → API → `SystemReportInput` adapter → `assembleSingleReport`／`assembleMultiReport`。紫微沿用同一形狀。農曆換算已有 `lunar-typescript@1.8.6`（`bone.ts` 使用），但沒有紫微安星。

與八字的既有行為對照（已核對程式）：八字晚子時「日柱不換日、只有時干隔日」，出生時刻為標準時間、無真太陽時，換年以節氣（立春）。紫微換年以農曆正月初一，因此兩系統的年份歸屬可能不同。

## Goals / Non-Goals

**Goals:**
- 可驗證的排盤：同輸入同輸出，不依賴現在時間、裝置時區、外部 API。
- 命盤事實、固定內容、ontology mapping 三者分離、各自版本化。
- 與其他命理系統一致地進入單維度與綜合報告，且每個句子可追溯來源。
- 語氣符合全站保守措辭規則。

**Non-Goals:**
- 煞星與四輔星以外的輔星、亮度、大限流年、飛星、合盤、真太陽時（皆列後續）。
- 不改現有八字行為，不為紫微調整八字的換日規則。
- 不新增命盤持久化、不新增 Firestore collection。

## Decisions

1. **規則集中為 `ZIWEI_RULES` 與 `ZIWEI_ALGORITHM_VERSION`（目前 `sanhe-v2`）。**
   包含：流派、換年（`lunar-new-year`）、閏月（`split-at-day-15`）、晚子時（`same-day`）、時間（沿用 `BirthMoment`）。算法或四化表任何變動都升版。四化表以十天干 × 祿權科忌的明確資料表保存，來源單一、不混用。四化表、命主、身主與四輔星安星統一採通行規則（無原書頁面，以 iztro 開源實作為對照來源，並依使用者 2026-11-11 的指示標為已核對）；命主以**命宮地支**查表（通用規則，與 iztro 通用設定及使用者提供的兩張科技紫微網命盤一致；iztro 的 `zhongzhou` 設定改用生年支，被 1983 年那張盤排除，原先曾依此設計並於此升版 `sanhe-v2`），身主以生年支；每張表附 `RuleVerification`（status／來源／版次／頁碼／備註），全部為 `verified`（與 iztro 2.6.5 比對一致，並依使用者 2026-11-11 的指示標為已核對，備註如實記錄「沒有使用者確認的命盤」）；日後新增的規則表先標 `pending`。正式排盤入口 MUST 先呼叫 `assertRulesVerified`，有未核對的表就明確拋錯，不默默使用。

2. **排盤是純函式，位於 `shared/utils/ziwei/`，與八字日期判定分離。**
   不呼叫 `dayPillarOf` 等八字函式；只共用輸入型別 `BirthMoment` 與標準時間定義。農曆年月日與閏月旗標由 `lunar-typescript` 提供，一個薄的 adapter 負責轉成內部型別並檢查年份範圍。替代方案：直接共用八字日柱判斷——否決，八字算法調整時會連帶改變紫微。

3. **閏月月中分界：閏月 1–15 日歸原月，16 日起歸下月；命盤 metadata 記錄 `isLeapMonth`、`originalLunarMonth`、`effectiveLunarMonth`。** 邊界日（15、16）有測試；UI 對閏月出生者提示「各派算法不同，可能有差異」。

4. **晚子時日期不換日。** 23:00–24:00 的農曆日沿用當天，時支為子；與八字一致，避免兩個系統日期歸屬矛盾；UI 在該時段與時辰交界（距交界 ≤ 15 分鐘）顯示提示，沿用 `BorderlineNote` 的作法。

5. **命盤資料模型。** 十二宮各含宮名、地支、主星、輔星（文昌、文曲、左輔、右弼；四輔星依生時與有效農曆月安星）、四化標記（四化是星的屬性，主星或輔星皆可帶，不是額外的星）、是否空宮；空宮只看主星，輔星不算主星；空宮不寫入借來的星。`bodyPalace` 只記錄身宮所在宮位與其與命宮的關係。借星為解讀層的衍生資訊（`borrowedFromPalace`、`borrowedStars`），只借對宮主星、不借輔星，不寫入命盤事實。命主、身主、五行局納入命盤並顯示，算法與選定來源一併固定；其詳細解讀可延後。

6. **固定內容分層：** 主星 14、輔星 4、宮位 12、四化 4 各一則；命宮與身宮的解讀由「主星描述＋宮位語境」以模板規則組合（不是字串直接拼接，需有組合測試確認不重複、通順）；不做 14 × 宮位的全組合。金鑰規則擴充於 `fixedContentKeys.ts`，內容走 `content:import`。每則標記排盤算法來源、解讀依據、內容版本、審稿狀態與撰寫方式。來源與審稿紀錄放在匯入檔（版本控制）的 `provenance`（算法來源、解讀依據、撰寫方式 `ORIGINAL`／`AI_DRAFT`、審稿者），匯入時檢查，不寫入 Firestore 文件；狀態不是 `DRAFT` 時必須有審稿者，所以 AI 起草而未審的內容只能是 `DRAFT`、不會被使用者讀到。固定的免責文案不納入措辭檢查（它含「必然」），但必須與規定的文字一字不差。

7. **Ontology：keyword mapping，來源類型獨立 `ziwei`。** 14 主星、4 輔星與四化各自指向少數特質軸端點；四化可加少量結構規則，化曜落在輔星時一樣可推論。只從「畫面上顯示的事實」推論，不從借星推論。紫微不與八字合併計票（`SOURCE_BY_SYSTEM` 不使用 `chinese-metaphysics`）。找不到合理對應的星不強制對應。

8. **不另存命盤。** 命盤由出生資料即時計算；`reportSnapshot` 依 `ZIWEI_ALGORITHM_VERSION` 與內容版本判斷重用或重存，與現有報告一致。替代方案：另存 `chartData`——否決，與純函式原則重複、並增加 TTL 與清除成本。

9. **語氣驗證：** 沿用全站措辭檢查（含「可能／傾向」、禁診斷與財務用語），新增紫微專屬規則（禁「大凶」「早逝」「必」「破財」；化忌不得描述為災難或壞事預告，文昌、文曲化忌不得寫成考運或表達的壞事預告）；固定內容匯入前跑檢查。報告固定標示「象徵性解讀，非科學測量；內容適合自我探索，不代表必然發生的事件」。

10. **API 與存取：** `POST /api/ziwei/calculations`，public、zod `safeParse`、response schema `parse`，與八字同型；於 `routeAccess.ts` 加規則。缺出生時間回傳明確驗證錯誤。

11. **入口開關預設關閉**，內容完整匯入並完整檢查一次後才開。

## Risks / Trade-offs

- [命宮算錯整份報告皆錯] → 單元測試（十二時辰、十二命宮地支、五行局完整覆蓋、十天干四化表、昌曲左右的十二時辰與十二月覆蓋、命宮與身宮同宮與不同宮）、邊界測試（閏月、晚子時、時辰交界、跨年、農曆年初年末）、至少 10 組已知命盤對照（記錄來源與算法設定）；原訂其中至少 3 組由使用者確認，已依使用者 2026-11-11 的指示免除，改以 iztro 4192 組比對取代。
- [各流派結果不同，使用者以其他軟體對照而質疑] → 標示採用規則與版本，UI 說明簡化版範圍（無輔星、無亮度、無行運），閏月與晚子時提示。
- [與八字的年份歸屬不同造成困惑] → 兩者各自標示依據，不使用共用的「年柱」欄位，不做交叉比對。
- [吉凶用語與全站規則衝突] → 內容自撰並過檢查，審稿後才匯入。
- [輸入年份超出農曆套件可靠範圍] → 先實測支援範圍，超出時拒絕並提示；加農曆與公曆往返測試，並與第二個獨立曆法來源交叉驗證。實測：`lunar-typescript@1.8.6` 於 1901–2099 逐日可用（支援範圍定為此區間）。以香港天文台（HKO）公曆與農曆對照表逐日比對 72,684 天：僅 2057-09-28 至 2057-10-27 共 30 天不一致（HKO 九月初一為 9/28，套件為 9/29，月初差一天），其餘全部一致，含 1917、1922、1987 的閏月與各年春節；2057 為預測年份，不影響實際出生資料，以測試記錄此差異。Node ICU `chinese` 曆另有 417 天與兩者不一致，不採作基準。HKO 只驗證農曆日期，不決定排盤規則。
- [`lunar-typescript` 版本更新改變結果] → 版本鎖定在 package.json，回歸測試涵蓋已知命盤。

## Migration Plan

1. 合併程式碼，入口開關為 false。
2. `pnpm content:check` → `pnpm content:import content/fixed/ziwei.json --dry-run` → 正式匯入。
3. 實測命盤頁、單維度報告與含紫微的綜合報告後，開入口並部署。
4. 回滾：關閉入口開關；不涉及資料遷移。

## Open Questions

- 九張規則表已與 iztro 比對一致，並依使用者 2026-11-11 的指示標為 `verified`（沒有使用者確認的命盤）；守門機制保留，日後新增的規則表先標 `pending` 時正式排盤會拒絕執行。
- 晚子時：已實測，iztro 把 23:00–24:00（`timeIndex = 12`）的日期進到隔天，與本 change「不換日」（與八字一致）刻意不同；對照時晚子時不納入比對，各自以測試記錄。
- 使用者提供的兩張科技紫微網命盤（出生資料不留存於版控）：農曆、五行局、命主與身主、十二宮的主星輔星與四化全部吻合；其中一張的命主與依生年支查表的結果不同，排除了「命主依生年支」，改依命宮地支。測試改用 iztro 取樣的匿名樣本（十個年干各一、五組命主規則不同者）涵蓋同樣的特徵。
- iztro 2.6.5 對照結果：以 4192 組隨機（1901–2099）與邊界輸入（農曆換年、閏月十五與十六日）比對五行局、命主、身主、命宮與身宮地支、18 顆星的所在地支與四化，0 筆不一致。這只代表與一個開源實作一致；使用者於 2026-11-11 指示在沒有使用者確認命盤的情況下標為 `verified`，`RuleVerification.notes` 如實記錄此依據。
- 已決定：紫微基礎點數比照八字 3 點；`SINGLE_REPORT_TEMPLATE_VERSION`／`MAPPING_VERSION` 不升版。
- 命盤頁是否沿用八字的版面元件結構：預設沿用 `app/components/bazi/*` 的慣例，另建 `ziwei/` 目錄。
