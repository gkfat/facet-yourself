## Context

八字報告已分成「命盤資料」（由 `BaziResponse` 的確定性欄位畫出）與「命理解讀」（由 `shared/report/adapters/bazi.ts` 把固定內容組成報告區塊）兩層。命盤資料的計算在 `shared/utils/bazi/`（`facts.ts` 的 `findRelations`、`strength.ts` 的強弱、命格與喜用神），解讀內容是 `content/` 下事先審核的固定內容，鍵由 `termOfKey` 對到特質本體的 term。

現況缺口：命局關係只有天干五合、地支六合、六沖；格局只有月令本氣的十神；喜用神只有用神、喜神、忌神；沒有調候；人生面向是依特質作的通用推測。專案原則：計算是純函式、同輸入同輸出；解讀不呼叫 AI；報告句子必須帶 sources；措辭保守，不談吉凶。

## Goals / Non-Goals

**Goals:**
- 以固定、公開的規則補齊三合、三會、刑、破、害、格局的透干依據、仇神、閒神與調候，全部是可重現的事實。
- 為每個新事實提供事先審核的固定內容，放進「命理解讀」。
- 新增八字專屬的人生面向（性格、事業、財富、感情、人際、學習）固定內容。
- 報告註明採用的規則與「不同流派標準不同」。

**Non-Goals:**
- 完整的《窮通寶鑑》逐月逐日主取用規則，以及整合日主旺衰、格局與季節氣候的綜合喜用神分析。
- 神煞、流年運勢評分、任何吉凶、婚姻、健康、壽命、財運預測。
- 判定「破格、敗格」或「格局高低」：這類判斷流派分歧大，且等於評分。
- 以 AI 產生解讀內容。
- 已完成的報告分區、章節導覽與命局關係卡（合與沖）的畫面。

## Decisions

**1. 規則以常數表加純函式實作，固定採用一套子平通行規則**
三合（申子辰、亥卯未、寅午戌、巳酉丑）、三會（寅卯辰、巳午未、申酉戌、亥子丑）、六合、六沖、刑（寅巳申、丑戌未、子卯、自刑）、破、害都放在 `shared/constants/bazi.ts` 的表，函式只查表。
替代方案：做成設定檔讓使用者選流派。否決：報告需可重現，多流派會讓快照、固定內容與測試數量成倍增加。

**2. 三合只取全三合與「含旺支的半合」，並標示是半合**
需要四柱中同時出現三個地支才算三合；兩個地支且含子、卯、午、酉其一時算半合，輸出時分開標示。
替代方案：只收全三合。否決：八字只有四個地支，全三合很少見，使用者幾乎看不到結果。半合在報告與畫面獨立標記，不直接等同完整三合局（已確認收錄）。

**3. 格局只輸出「取格依據」與「透干與否」，不判成敗**
取格仍以月令本氣為準（沿用現有命格），新增「月令藏干是否透出在其他天干」的事實與依據句。格局特徵解讀沿用並擴充 `pattern_*` 固定內容。
替代方案：實作成格、破格判斷。否決：標準不一，結果等同高低評分，違反不評吉凶的原則。

**4. 仇神與閒神以五行關係從喜用神與忌神推得**
把十神類別換算成相對日主的五行，忌神所對應的五行中，生忌神者為仇神，其餘不在用、喜、忌、仇的類別為閒神。中和時不列任何一項，與現行規則一致。規則寫成表與測試，避免多個忌神時結果不一致。

**5. 調候做成「季節氣候分析」簡化模型，只處理三個層次，不承擔完整取用規則**
模組命名為「季節氣候分析」，不叫「《窮通寶鑑》喜用神」；思想來源是《窮通寶鑑》的調候，但第一階段不做十個日主乘十二個月份的完整取用。報告 MUST 標註「簡化調候模型」，並註明力量分級是產品自訂的量化標準，不是《窮通寶鑑》的傳統判定門檻，避免使用者誤以為是逐月逐日主的完整取用結果。已審核確認的規則：

1. **月份氣候表**（溫度、濕度、氣候偏向分開記錄）：亥子丑＝寒、濕、偏寒；寅＝涼、平、無；卯＝溫、平、無；辰＝溫、濕、無；巳午未＝熱、燥、偏熱；申酉戌＝涼、燥、偏燥。丑已在寒濕月份不另調整；辰保留溫濕，暫不判定偏濕；日後若加「偏濕」判斷，不改月份表。
2. **火、水力量**：沿用日主強弱的位置權重算法（藏干按本氣、中氣、餘氣比例，日主自身的天干不計），得到 0 到 100 的「相對力量指標」（不是火、水各佔八字的實際百分比）。分級：0＝沒有；1 到 14＝弱；15 到 34＝中；35 到 54＝強；55 以上＝過旺。通根與透干已反映在權重中。
3. **調節條件**（暖局看火、潤燥看水）只有三種結果：不足（沒有或弱）、適中（中或強）、過旺。火過旺不代表暖局更好，可能過度燥熱；水過旺不代表潤燥更好，可能形成寒濕。
4. **調候狀態**：
   - 偏寒月份（亥子丑）：火不足→偏寒、暖局需求較高；火適中→相對平衡；火過旺→標記「暖局過度，可能偏熱」。
   - 偏熱月份（巳午未）：水不足→偏熱（燥熱）、潤燥需求較高；水適中→相對平衡；水過旺→標記「潤濕過度，需結合寒暖判斷」。
   - 偏燥月份（申酉戌）：水不足→偏燥、潤燥需求較高；水適中→相對平衡；水過旺→標記「潤濕過度」。
   - 春季（寅卯辰）：預設相對平衡，仍檢查下面兩條極端失衡。
   - 任何月份、且上面規則得到相對平衡時：火過旺且水不足→偏熱、降溫需求較高；水過旺且火不足→偏寒、暖局需求較高（不標偏濕）。
5. **合沖不調整分數**，只標註「火受合、水受合、火受沖、水受沖」，報告寫「實際作用需結合整體命局判斷」。

輸出結構拆成氣候狀態與調節條件：`seasonalClimate` 含 `month`（月支）、`temperature`、`humidity`、`monthBias`（cold／hot／dry／none）、`elements.fire / water`（各有 `present`、`power`、`level`）、`regulation.warming / moistening`（`insufficient`／`moderate`／`excessive`）、`status`（cold／hot／dry／balanced）、`needs[]`（warming／cooling／moistening）、`excess[]`、`influences[]` 與 `summary`。解讀只描述傾向與需求高低，不指示補什麼五行、不建議改運。
替代方案：只用月份機械地判定寒熱燥濕。否決：同一個月份的命盤，火水的有無與強弱會讓結果不同。替代方案：完整實作《窮通寶鑑》逐月逐日主取用。否決：規則量大、各版本不一，風險與審核量遠超第一階段。
綜合喜用神（把日主旺衰、格局、季節氣候整合）留待未來，不在本 change。

**6. 人生面向以「偏多的十神類別 × 面向」為鍵，內容由 Claude 起草、使用者審核**
鍵為 `life_<面向>_<類別>`，面向六個、類別五個加「平均」共 36 筆，內容事先撰寫與審核。選十神類別當維度是因為傳統上它對應事業（官殺）、財（財）、學習（印）等，不需要新增計算。內容在「命理解讀」的人生面向區顯示，並明講是傳統說法。

**7. 新內容缺失時不讓命盤 API 失敗**
現行規格是所需固定內容未發佈就回 404。新增的內容欄位改為「缺少時該項解讀省略」，不影響既有欄位，讓程式可先於內容匯入上線。既有 123 筆的行為不變。

**7b. 新增的解讀不新增特質 term，也不新增互動規則**
專案已定：喜用神是「較順手的方向」不是特質，所以不映射到特質軸。透干、仇神、閒神、季節氣候講的同樣是方向、需求與依據，因此只作為「命理解讀」的卡片，不新增 term、映射或互動規則；人生面向以十神偏多的類別為鍵，沿用既有的 `bazi:group:*` term 當來源。結果是 `ONTOLOGY_VERSION`、`FRAGMENT_VERSION`、`MAPPING_VERSION`、`INSIGHT_RULES_VERSION` 都不用升，只升報告模板版本。
替代方案：為這些事實新增 term 並映射到特質軸。否決：會把「方向」當成特質推論，與喜用神的既有做法不一致，也會增加需要審核的映射。

**7c. 以兩份印出的命盤校正既有規則**
拿兩份印出的命盤（參考案例一 06:00 男、參考案例二 04:00 女）逐項對照後，校正下列規則，其餘（四柱、十神、藏干、十二運星、空亡、胎元、強弱、格局、大運、流年）本來就一致：
- **五行力量**：報告的五行是加權的，且可以完全重現（天干 5、地支 8 依藏干 5：2：1 分配、月令加倍，共 60，兩份命盤的金木水火土全部吻合）。五行「缺少」改以力量為 0（含藏干）為準，原本只看天干與地支本氣，會把申裡的壬判成缺水，並與季節氣候的算法自相矛盾。
- **喜用神**：改成由五行力量推得（見上方規格），原本依命格查固定表。兩份命盤共十個判斷全部吻合；規則是從這兩份歸納而來，樣本少，需要更多命盤驗證。
- **命宮**：改用「月將加時」，月將以中氣換，原本用節氣月，兩份命盤都落在中氣之後，系統都早一個地支。與 lunar-typescript 的交叉比對改成：月的前半（節到中氣）兩者相同，後半（中氣之後）地支差一位。
- **巳的藏干**：改成丙、戊、庚（原為丙、庚、戊），與印出的命盤與《三命通會》一致；其餘八個有藏干中氣餘氣的地支兩份命盤都一致。
- 「喜用神說明」固定內容由 10 筆（依命格與強弱）改成 2 筆（身強、身弱），具體的類別由畫面上的磚塊呈現。
替代方案：維持原規則並在畫面註明差異。否決：使用者以印出的命盤為標準。

**8. 回應 schema 只新增欄位，不改既有欄位**
`BaziResponse` 新增關係種類、格局依據、仇神、閒神與調候欄位；前後端共用 `shared/schemas/api/bazi.schema.ts` 解析，前端沿用 `BaziChartPanel` 的卡片。報告 adapter 的新解讀走既有 `card()` 與 `termOfKey` 路徑，不新增區塊種類，所以 AI 詳細報告會自動讀到新增句子。

## Risks / Trade-offs

- [流派標準不一致，使用者拿別的網站比對會不同] → 固定一套規則，報告與規則說明明確寫出採用的版本與差異。
- [人生面向 36 筆內容撰寫與審核量大] → 先以已有的十神群組內容為底稿，由人審核；未審核完的面向不顯示，不補空話。
- [人生面向容易滑向預測或診斷] → 沿用 `insightRules/validate.ts` 的措辭檢查（需含「可能／傾向」、禁用診斷與財務用語），並對新內容跑同一套檢查。
- [刑破害結果多，畫面變雜] → 以「關係」為單位列出，每項一句白話，沒有時只寫沒有。
- [新增 sources 與 term 增加 ontology 維護量] → 只為顯示在畫面上的事實新增 term，跑 `pnpm ontology:check` 與 `shared/report/synthesis.test.ts`。
- [既有已存報告快照與新內容不一致] → 升版本常數，`reportSnapshot.service` 依內容重用或重存。

## Migration Plan

1. 先合併計算與 schema（欄位新增、不改舊欄位）。
2. 匯入新的固定內容（`pnpm content:import`），內容缺少時畫面省略。
3. 升版本常數並上線；舊快照會依版本重存。
4. 回復：只需還原程式，新增欄位被前端忽略不影響其他功能；固定內容可保留在資料庫。
