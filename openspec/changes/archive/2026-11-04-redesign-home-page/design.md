## Context

- `app/pages/index.vue`：Hero（標題「我是誰？」、長段 lead、徽章、登入區）→ `angles` 卡（兩個 system 各列所有項目）→ `FortuneHomeEntry` → `fill` 卡（出生日期、血型、進階資料）→ 「可做的分析」卡（兩個 system 各一列卡片，按鈕依資料是否齊全啟用）→ 多維度卡（以 `gated` 模糊並覆蓋登入提示）。
- 資料來源：`useProfile`（會員資料或 guest session，停止輸入一會兒後存檔）、`useExploration`（`state`、`progress.multiDimensionUnlocked`）、`assessmentCards()`、`BAZI_ENTRY_ENABLED`／`KIN_ENTRY_ENABLED` 旗標。
- 星座與生命靈數可在前端以 `zodiacFromIsoDate`、`lifePathNumber` 算出；它們的固定內容由既有的公開 API 提供（`/api/fixed-results/zodiac`、`/numerology/{number}`），但各回傳整份內容（含長篇欄位），預覽只需要標題與一句摘要，且兩個請求分開。
- `RateLimitService`（Firestore 固定窗口，每次消耗是一個 transaction）與 `getClientIp`、`keyedHash` 已有範例用法（`POST /api/guest-sessions`）。`FixedContentService.getPublished` 每次讀一次 Firestore。
- 專案規定：除 `guestSessions`／`welcomeGrants`／`rateLimits` 外不開 TTL；新增 API 路徑必須檢查 `routeAccess.ts`。
- `/pricing` 已有「3 維度分析」量尺（`ZODIAC`+`MBTI`+`NUMEROLOGY`）與 `multiReportCost`。
- `FortuneHomeEntry` 已對訪客顯示「看今天的運勢」導向 `/fortune`；`GuestNotice` 與 `useViewer` 可重用。

## Goals / Non-Goals

**Goals:**
- 訪客一進首頁就能輸入出生日期，並立刻看到第一個結果（甜頭在前）。
- 分析入口從「十幾個平鋪、列兩次」變成「兩類系統、所有入口只出現一次」，每個入口只出現一次。
- 今日運勢進入第二屏，作為回訪鉤子。
- 多維度分析被說明清楚，並連到 `/pricing`，不再以模糊遮住。

**Non-Goals:**
- 範例報告、社會證明、行銷素材。
- 變更各分析頁、`/pricing`、header nav。
- 新增 API 或後端邏輯。
- 重新設計視覺系統（沿用現有的色票、`ReportBanner` 以外的 hero 背景、卡片樣式）。

## Decisions

### D1：區塊順序為「Hero → 今日運勢 → 多維度分析 → 從你的生日開始 → 預覽 → 認識自己」，一列一項
Hero 只留標題與副文案；其後每個區塊各佔一列、與頁面同寬：今日運勢、多維度分析、單一張「從你的生日開始」卡片（出生日期、補充資料、訪客的登入促進都在同一張卡片內）、即時預覽（有日期才出現）、分析入口。

- 理由：先給兩個「留下來」的理由：每天都不同的運勢（回訪）與疊起來看的多維度報告（深度與點數）；再請對方填個資並看單一維度的結果。一列一項讓閱讀順序單純，不需要在並排的兩塊之間比較視覺份量。
- 視覺分工：今日運勢是琥珀色的淺色卡片（每天會變）；多維度是深藍色的滿版色帶（背景延伸到螢幕兩側、文字仍在欄寬內，視覺主角），以三個互相重疊的圓表示「多個維度疊在一起，中心是你」，載入時圓從分開滑到重疊一次。兩張卡片都以自己的寬度（container query）決定排版，全寬時今日運勢的小卡一列四張、多維度的文字與圖左右並排。
- 取捨：出生日期的輸入被移到頁面較下方，訪客要捲過兩張卡片才看到；因此今日運勢與多維度對訪客都不需要先填資料（運勢可直接試、多維度說明完整可讀），登入促進則留在填個資的卡片內，不在上方重複。
- 替代方案：把今日運勢與多維度並排成一列。否決：使用者要求一列一項。

### D2：即時預覽的名稱由前端算，摘要由一支首頁專用 API 一次取得
預覽卡顯示「你是 {星座}」與「生命靈數 {數字}」（前端算出，立即出現），各帶前往 `/full-report/zodiac`、`/full-report/numerology` 的連結；名稱出現後，前端以**一次請求**向新的 `GET /api/home/preview?sign=&lifePath=` 取得兩者的標題與一句摘要。沒有日期、日期不完整或無效時不顯示。

- 請求只帶星座名稱與生命靈數的數字，**不帶出生日期**。
- 首頁因此對預覽只有一個公開請求（原本會是兩個），且回應只含標題與摘要，比整份固定內容小得多。
- 前端以 `(sign, lifePath)` 為鍵在記憶體快取；日期變了但兩個值沒變不重新請求；輸入過程以短暫延遲合併（只在日期完整有效後才請求）。
- 摘要載入中時名稱已經可見；請求失敗、被限流（429）或內容尚未發佈時，只顯示名稱與連結，不顯示錯誤、不重試、不用自編的內容補。
- 替代方案：沿用兩個既有端點。否決：請求數加倍，回應包含用不到的長篇內容，也沒有針對首頁的防護。
- 替代方案：POST 帶出生日期、由伺服器算。否決：出生日期是敏感資料，不該為了一句摘要送上伺服器或進入日誌；名稱與數字前端本來就算得出。

### D3：兩類系統的所有分析直接呈現，不推薦、不折疊
「從不同的角度認識自己」依「命理與象徵系統」「人格與心理特質」兩類分組，每組保留「目的」一句話，直接列出該類所有已啟用的入口，每列三欄（md 以上）；沒有「推薦」「更多角度」之類的子標題。旗標關閉的項目（八字、瑪雅 Kin、各自我分析）本來就不在清單中，某一類沒有任何入口時整類不顯示。

- 理由：使用者要在首頁一眼看到所有測驗與分析方式；推薦清單與折疊都讓部分入口被另眼看待或需要點擊，與「直接呈現」的要求相反。取消後也不需要為推薦清單寫遞補規則。
- 取捨：頁面變長，卡片約 15 張。兩類分組與目的說明提供閱讀順序；`/self-reports`（自我探索）仍完整列出。
- 演進：先是「3 個推薦 + 折疊」，再改成「推薦在前、其餘攤開」，最後取消推薦，因為推薦的 3 個與下面的分組重複列出了同樣的入口。
- 合併後 `systems` 與 `analyses` 兩份資料保持單一來源，卡片從同一份產生，不再各列一次。

### D4：沿用現有的卡片與按鈕狀態
分析卡的「可用／鎖定」判斷（`ready`、`lockedHint`、`need`）完全沿用，只改它出現的位置與數量。補充資料展開區沿用 `ProfileBirthTimeSelect`、`ProfileCitySelect`、血型與性別欄位與同一組 `useProfile` 綁定，不改儲存行為。

### D5：多維度區塊是視覺主角，說明加入口，不再鎖定
移除 `locked`／`gated` 的模糊與覆蓋層。多維度區塊成為與今日運勢同列、較寬的深色卡片：標題「把幾個角度疊在一起看」、一段說明、重疊圓的圖、按鈕與「2 個維度 N 點起」。按鈕：已解鎖者前往 `/report`；未解鎖者顯示「先完成 2 個維度」（停用）；另有連到 `/pricing` 的文字連結。N 由 `multiReportCost` 對最便宜的兩個維度算出。訪客在區塊內只看到一個「登入即贈 3 點」的小連結，登入促進的主體在 Hero 的卡片內，不在此處重複成提示框。

### D6：贈點說明用定價函式，量尺與 `/pricing` 共用
「首次登入贈 3 點，約可做 N 份 3 維度分析」的 N 由 `WELCOME_POINTS` 與 `multiReportCost` 算出。把 `/pricing` 的量尺常數抽到共用位置（`shared/`），首頁與 `/pricing` 引用同一個，避免兩處各寫一份。N 小於 1 時只顯示「首次登入贈 3 點」。

## Risks / Trade-offs

- [預覽的摘要是一個新的公開端點，可能被濫用] → 見 D8 的分層防護；失敗、被限流或內容未發佈時前端降級為只顯示名稱，不影響預覽出現。
- [分析卡片全部呈現後頁面較長] → 依兩類分組並保留各組的目的說明；`/self-reports`（自我探索）仍完整列出。
- [CDN 快取讓內容更新延遲最多一小時] → 預覽摘要可接受；完整分析頁不受影響，仍走原本的端點。
- [對函式本身的洪水無法僅靠程式擋下] → 上線前在 Vercel Firewall 為 `/api/home/preview` 設速率規則（tasks 中列為檢查項）。
- [記憶體快取是 per-instance，冷啟動後全部 miss] → 合法輸入組合有限，冷啟動後的 miss 數有上限，且 miss 路徑有限流。
- [index.vue 約 990 行，改動大] → 拆出預覽卡與分析清單兩個小元件，index.vue 只負責組裝與資料；一次只動一個區塊並跑 lint。
- [既有 spec 提到首頁卡片的措辭與新結構不一致] → tasks 中逐條對照，必要時補 delta 後再歸檔。

### D8：首頁預覽 API 的防護分層
`GET /api/home/preview` 是公開、免登入的端點，可能被拿來灌流量或放大 Firestore 讀取，因此依成本由便宜到昂貴分層擋：

1. **輸入驗證（最先、最便宜）**：`sign` 必須是 12 星座之一，`lifePath` 必須是 1–9、11、22、33；至少一個，其餘參數忽略；不合法回 400，不碰 Firestore。合法輸入的組合只有有限個（12 × 12），這是後面快取有效的前提。
2. **CDN 快取**：200 的回應帶 `Cache-Control: public, s-maxage=3600, stale-while-revalidate=86400`，相同的查詢由 Vercel edge 回答，不進函式；4xx 與 429 一律 `no-store`，不被快取。內容重新匯入後最多一小時才會在首頁更新，預覽可接受。
3. **伺服器端記憶體快取**：以 `類型:鍵` 為鍵的 per-instance TTL 快取（有內容約 10 分鐘，未發佈的 `null` 約 1 分鐘），讓同一個實例內重複的 miss 不再讀 Firestore。
4. **限流只套在「需要讀 Firestore」的路徑**：記憶體 miss 時，才以 IP 的 keyed hash 呼叫 `RateLimitService.consume`（例如每 IP 每分鐘 60 次，常數可調），超過回 429。
   - 理由：限流本身是一個 Firestore transaction，若套在每個請求上，攻擊者反而能靠請求製造寫入；而快取命中的請求不碰 Firestore，成本低，不需要計數。合法輸入組合有限，真正會 miss 的只有冷實例與過期的第一次，所以這個限額對正常使用幾乎碰不到。
   - IP 無法判斷時（`'unknown'`）共用一個桶，被限流時前端降級為只顯示名稱，不影響預覽出現。
5. **基礎設施（不在程式範圍）**：對函式本身的呼叫洪水，需要 Vercel Firewall 的速率規則；列為風險與上線檢查項，不在此用程式處理。

- 回應一律只含 `title` 與 `summary`（各自可為 `null`），不含其他欄位，也不回傳任何使用者資料。
- 此端點不讀、不寫任何使用者資料，不需要也不使用 guest session。
- 替代方案：每個請求都限流。否決：見上，會把便宜的請求變成 Firestore 寫入。
- 替代方案：只做 CDN 快取。否決：CDN 對 4xx 與冷快取的第一次請求沒有保護，且無法保證所有流量都經過 CDN。

### D7：Hero 標題（已確認）
- Hero 標題為「各種面向綜觀自我，更進一步了解自己」；副文案縮成一句，說明從你好奇的角度開始，實作時沿用現有語氣撰寫，不再列功能清單。
- 原本確認的「推薦入口固定為星座、生命靈數、MBTI」已因取消推薦而不再適用（見 D3）。
